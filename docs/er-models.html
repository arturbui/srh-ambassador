Four ER models, one rights system

This is the data model behind the SRH Ambassador CMS (Strapi 5), split into the four domains it's actually built from, plus the roles-and-rights layer that governs who may read, write, or approve what — across both the public API and the admin back office.

1 Clubs, categories & documents

The club registry

Every club sits under one category and can hold a set of uploaded documents (statutes, membership forms, handouts) with their own visibility tier. 

%%{init: {'theme':'base', 'themeVariables': {'primaryColor':'#fbfaf6','primaryTextColor':'#1b2321','primaryBorderColor':'#2f5d45','lineColor':'#2f5d45','secondaryColor':'#efebde','tertiaryColor':'#fbfaf6','fontFamily':'Georgia, serif'}}}%%
erDiagram
    CATEGORY ||--o{ CLUB : groups
    CLUB ||--o{ DOCUMENT : owns
    CATEGORY {
        string name
        text description
    }
    CLUB {
        string name
        blocks description
        string hostName
        enum approvalStatus "pending, approved, rejected"
    }
    DOCUMENT {
        string title
        text description
        media file
        enum visibility "public, members, leaders"
    }

Reading this model

  • Approval is a gate, not a field. A club is always created with approvalStatus = pending; the public API refuses to accept any other value on create or update, so a club can only move to approved from the admin panel.
  • Documents carry their own visibility (public / members / leaders), independent of the club's own approval state — a pending club's leader can still stage internal paperwork before launch.
  • A club also anchors Activities and Memberships, shown in their own models below.
2 Events & activities

Two kinds of "happening"

Club activities are recurring, room-booked sessions; events are one-off and hosted directly by a user, with their own attachable materials. 

%%{init: {'theme':'base', 'themeVariables': {'primaryColor':'#fbfaf6','primaryTextColor':'#1b2321','primaryBorderColor':'#2f5d45','lineColor':'#2f5d45','secondaryColor':'#efebde','tertiaryColor':'#fbfaf6','fontFamily':'Georgia, serif'}}}%%
erDiagram
    CLUB ||--o{ ACTIVITY : runs
    USER ||--o{ EVENT : hosts
    EVENT ||--o{ MATERIAL : attaches
    ACTIVITY {
        string title
        blocks description
        datetime date
        string location
        string building
        string room
        integer capacity
        text timetable
    }
    EVENT {
        string name
    }
    MATERIAL {
        string name
        boolean organizerProvided
        media file
    }
    USER {
        string username
        string email
    }

Reading this model

  • Activities are club-scoped; the schema has no Club↔Event link, so a general campus event and a club's recurring activity are deliberately tracked as separate things.
  • Ownership is forced server-side. On create, event.host is always set to the requester's own account — a client can never assign an event to someone else.
  • Material's file is a real upload (image, video, audio, or document), repeatable per event.
3 News & content

Editorial content

The simplest model: an article, written by one user, tagged as an announcement or a report. 

%%{init: {'theme':'base', 'themeVariables': {'primaryColor':'#fbfaf6','primaryTextColor':'#1b2321','primaryBorderColor':'#2f5d45','lineColor':'#2f5d45','secondaryColor':'#efebde','tertiaryColor':'#fbfaf6','fontFamily':'Georgia, serif'}}}%%
erDiagram
    USER ||--o{ NEWS_ARTICLE : authors
    NEWS_ARTICLE {
        string title
        enum category "announcement, report"
        blocks content
    }
    USER {
        string username
        string email
    }

Reading this model

  • Images live inside the article — content is a Strapi Blocks field, so inline images are embedded in the rich-text tree rather than a separate media relation.
  • Authorship is forced server-side the same way event hosting is: author is always the requester, never client-supplied.
  • Only a Content Editor (or admin-panel staff) can create, edit, or delete an article — a plain authenticated user can only read.
4 Users, roles & permissions

Two parallel rights systems

Strapi keeps back-office staff and public-facing users in entirely separate tables, each with its own role model. "Club leader" isn't a role at all — it's read off membership.role, per club. 

%%{init: {'theme':'base', 'themeVariables': {'primaryColor':'#fbfaf6','primaryTextColor':'#1b2321','primaryBorderColor':'#2f5d45','lineColor':'#2f5d45','secondaryColor':'#efebde','tertiaryColor':'#fbfaf6','fontFamily':'Georgia, serif'}}}%%
erDiagram
    CLUB ||--o{ MEMBERSHIP : roster
    USER ||--o{ MEMBERSHIP : joins
    UP_ROLE ||--o{ USER : assigned
    ADMIN_ROLE ||--o{ ADMIN_USER : assigned

    MEMBERSHIP {
        datetime joinedDate
        enum role "member, leader"
    }
    USER {
        string username
        string email
    }
    UP_ROLE {
        string name "Public, Authenticated, Club Leader, Content Editor"
        string type
    }
    ADMIN_USER {
        string firstname
        string lastname
        string email
    }
    ADMIN_ROLE {
        string name "Super Admin, Editor, Author, Club Administrator, News Moderator"
        string code
    }

Reading this model

  • USER and ADMIN_USER are different tables (plugin::users-permissions.user vs admin::user) — a club leader logging into the public API and a staff member logging into /admin are unrelated accounts.
  • Leadership is contextual, not a role. One person can be leader of Robotics Club and a plain member of Chess Club at the same time — every club-scoped policy checks membership.role for that specific club, not a global flag.
  • The full action-by-action breakdown for both role systems is the permission matrix below.

What each Users-Permissions role can do on the public REST API, and what each admin-panel role can do in the Content Manager. A scoped chip means the static permission only grants the action conditionally — enforced by a row-level policy, not by the role alone.

Row-level policies referenced above

¹ is-club-leaderClub update — only if the requester has a leader membership on that specific club.
² is-activity-club-leader / is-document-club-leaderActivity and Document create/update/delete — same leader check, resolved via the record's own club (or the club named in the request body, on create).
³ is-ownerEvent update/delete — only the event's own host.
⁴ is-authorNews Article update/delete — only the article's own author.
⁵ document visibilityEnforced in the controller, not a policy: public documents are open to everyone; members requires a membership in that club; leaders requires a leader membership; the uploader can always see their own.
⁶ is-self-or-club-leaderMembership read/delete — a member can see and leave their own membership; a club's leader can see and remove any membership on that club.
⁷ is-membership-club-leaderMembership update (e.g. promoting a member to leader) — only that club's own leader.
